# S0 audit

Reviewed completed tasks T001–T012 against `tasks.json`, `PRD_V2.md`, `design.md`, `rules_strictly.md`, and their listed artifacts. This was a source and evidence review; no product code, task status, or test suite was changed. S0 should not be considered fully verified while the findings below remain.

| Task | Severity | Unmet requirement and evidence | Recommended fix |
|---|---|---|---|
| T004 | Critical | Backup restore re-deletion cannot work as specified. The policy requires an out-of-band, append-only deletion registry, but `reapplyDeletions` reads `deletion_registry` from the same restored database (`packages/server/src/db/reapply-deletions.ts:7–9`; schema in `001_initial_schema.sql:377`). A backup predating deletion also predates its registry row, so the deleted account is resurrected. | Persist deletion tombstones outside the restored database, read that durable source during restore, and prove the before-deletion-backup scenario before admitting traffic. |
| T005 | High | Reproducible staging/production configuration and separation of API from execution workers are not established. `packages/server/src/db/database.ts:9–29` opens every `DATABASE_URL` as `node:sqlite`, including the documented production PostgreSQL setting. `docs/operations/production-readiness.md:23,38` says execution is synchronous in the API process and no deployment/restore/rollback configuration exists. | Implement production database and worker adapters plus staged deployment/rollback configuration, or return T005 to in-progress until those requirements are met. |
| T008 | Medium | First visit follows the OS theme, whereas design §3.1 requires dark by default. The head script in `packages/web/index.html:27–44` uses `system` when no preference exists, and `packages/web/src/main.ts:83–90` repeats that choice. The head script does resolve the theme before first paint. | Default an unset preference to dark in both places while preserving the explicit System choice. |
| T009, T010 | High | Shared HTML renderers interpolate account/course text without HTML escaping. `packages/web/src/components/shells/AppShell.ts:75` inserts `displayName`; `packages/web/src/components/common/ContentTree.ts:39,71,104` inserts titles into markup and attributes. A user-controlled title/name containing markup can execute in the browser, violating the strict content-sanitization and data-safety rules. | Escape text and attribute values at render boundaries or use DOM text nodes; cover hostile display names and course/tree titles with a security check. |
| T011 | Medium | Universal state copy asserts successful local persistence without checking it: `renderOfflineBanner` always says “Changes are stored on this device” and `renderInfrastructureFailurePanel` always says “Your code is saved” (`packages/web/src/components/states/UniversalStates.ts:72–78,113–119`). Design §8 permits those claims only when storage/save is confirmed. | Pass actual persistence state into the components and render truthful wording for unconfirmed storage. |
| T012 | Medium | Design §9 assigns theory, video, quiz, and Python variants to the same `/learn/:enrollmentId/steps/:stepId` route. The route table instead exposes `/video`, `/quiz`, and `/code` suffixes (`packages/web/src/router/routes.ts:59–63`), changing the specified route meaning and allowing a route to select the wrong renderer for the step type. | Resolve the step type from authorized server data at the canonical step URL; keep attempts as the specified nested route. |

## Verification scope

I inspected the S0 decision records, trace, configuration, schema, authorization and pagination helpers, shared UI components, states, routes, theme bootstrap, and production-readiness evidence. Findings above are grounded in code paths and documented gaps; no broad test run or visual checkpoint was performed for this audit.
