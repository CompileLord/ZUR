# S1 audit — Phase A safe practice

**Verdict:** S1 and S1-M02 should not be marked `done`. The Phase A isolation and durability gate is unmet. This is a source review against `tasks.json`, `PRD_V2.md` §§6–7, 11–13, 15–18, and `design.md` shared rules and P04–P08/P15–P20/P42. Findings below are confirmed from the cited implementation; runtime deployment and browser accessibility were not independently verified.

| Task | Severity | Confirmed unmet requirement and evidence | Recommended fix |
|---|---|---|---|
| T020, T028 | **Critical** | The runner starts ordinary host `python` through `child_process.spawn` with a temporary working directory ([`runner.ts`](../../packages/worker/src/runner.ts), lines 43–65). There is no network namespace, filesystem boundary, read-only runtime, process limit, CPU limit, memory limit, or temporary disk limit. `-I` only changes Python import behavior. Student code can read host files and create children or network connections under the worker's OS privileges. This contradicts PRD §13 and the isolation claim in ADR-003. | Run each test inside a reviewed OS/container isolation boundary with denied network and host mounts, restricted UID, read-only runtime, cgroup/resource limits, process count and disk limits; verify adversarial probes against that actual boundary. |
| T020, T021, T028 | **Critical** | Student execution is invoked synchronously inside the API request through [`server.ts`](../../packages/server/src/server.ts) lines 403–455 → [`execution-service.ts`](../../packages/server/src/services/execution-service.ts) lines 434–449 → `processExecutionJob`. The request does not hand off to a separately running worker, and the API awaits all tests. This violates the separate isolated worker and accepted-ID/reconnect lifecycle required by PRD §§12.4, 13. | Move execution to a separate worker process/service consuming a durable queue. Return an accepted job ID immediately, then poll persisted status/results. |
| T021, T023 | **Critical** | [`completeJob`](../../packages/server/src/services/execution-service.ts) lines 317–389 unconditionally inserts a new attempt and writes a result; it does not check terminal status or worker lease and does not wrap attempt, progress, and job updates in one transaction. [`claimJobById`](../../packages/server/src/services/execution-service.ts) lines 405–429 can reclaim any job, including a completed one. Duplicate/late completion can create multiple attempts and overwrite the authoritative result, violating PRD §§12.5, 17 and the S1 gate. | Make claim and completion conditional atomic transitions tied to a lease token; transact attempt, progress, and terminal result together; return the stored receipt for a repeated idempotency key. |
| T021, T028 | **High** | [`recoverStuckJobs`](../../packages/server/src/services/execution-service.ts) lines 390–403 requeues expired jobs without a retry count or total-job deadline. [`claimNextJob`](../../packages/server/src/services/execution-service.ts) lines 277–309 also takes expired running jobs directly. A crashing job can retry forever; no 60-second aggregate deadline is enforced. ADR-003 says three retries, but the code has no such bound. | Persist retry count and absolute deadline; stop at the retry limit with one `INTERNAL_ERROR` or `TIME_LIMIT` result. |
| T024 | **High** | [`quota-service.ts`](../../packages/server/src/services/quota-service.ts) checks only user active count and per-minute history. [`enqueueJob`](../../packages/server/src/services/execution-service.ts) lines 78–111 inserts after separate checks. There is no global bounded queue, fair scheduler, atomic admission, or author-wide validation quota. Concurrent admissions can exceed the two-job limit. | Enforce user and global capacity within one transaction, add fair scheduling and author-wide quota, and reject overload before creating a job. |
| T019, T020, T022 | **High** | [`runner.ts`](../../packages/worker/src/runner.ts) decodes output with `Buffer.toString('utf-8')` (lines 113–114), which replaces malformed bytes, so invalid UTF-8 is not reported as the required output-format failure. The runner uses `options.wallTimeoutSeconds || ...` but does not enforce CPU/memory budgets. Custom stdin reaches `runPythonIsolated` without the per-test 64 KiB validation in [`worker.ts`](../../packages/worker/src/worker.ts) lines 29–32. | Validate byte lengths at admission, decode UTF-8 fatally, and enforce CPU/memory/time budgets in the execution boundary. |
| T026 | **High** | P15 renders a plain `<textarea>` and decorative line numbers ([`PythonWorkspacePage.ts`](../../packages/web/src/pages/learning/PythonWorkspacePage.ts), lines 173–205). There is no implemented syntax highlighting, bracket matching, editor search, undo/redo controls, indentation behavior, or stable editor model shown in this component. The task and PRD §12.3 require these editor capabilities. | Use a stable accessible editor integration or implement and verify each required capability, including keyboard shortcuts and theme/font controls. |
| T026 | **Medium** | Student-controlled example strings and custom stdin are interpolated without HTML escaping ([`PythonWorkspacePage.ts`](../../packages/web/src/pages/learning/PythonWorkspacePage.ts), lines 126–134, 223–224). A course example or prior custom input containing HTML can enter the page markup, contrary to the design's safe content and PRD §16 requirements. | Escape these values at output or render them through safe text nodes. |

## Verification limits

The audit inspected the named source and the S1 completion evidence, including ADR-003. I did not run the existing automated suites or a deployed sandbox attack. The source itself establishes the isolation, lifecycle, concurrency, editor, and escaping defects above. Identity/account tasks T013–T018 were not exhaustively behavior-tested here; their `done` status remains **unverified**, not disproven by this report. Stage S1 must remain open until its implementation and Phase A adversarial, reconnect, recovery, and accessibility checks pass on the real architecture.
