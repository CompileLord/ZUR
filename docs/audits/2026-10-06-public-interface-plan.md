## Direction and priorities

Bring the public entry pages into the same visual system as the learning app. The landing page uses a different logo mark, header arrangement, sign-in treatment, and theme selector from catalog/course pages. Its animated figure dominates the hero while the actual workspace example sits below. The account forms are already compact and coherent; preserve them and improve only their state handling and repeated copy.

**P1:** consistent public shell, visible product example, and the inconsistent access-denied screen. **P2:** catalog/course hierarchy, account copy, Help, and policy presentation. This is a design plan based on existing evidence, not a new capture run or legal-content review.

Use one public header with the same ZUR mark, Courses/For teachers/Help navigation, account entry, and theme behavior. Keep public content around 1040–1120px wide; account forms about 400px. Shared tokens should match the authenticated app. Keep course discovery available without forcing interest selection or account creation before browsing.

## Continuity, motion, and delivery

Reuse `PublicShell.ts`, `AccountShell.ts`, and shared state components across landing/catalog/help/policy/error routes. Consolidate the separate landing header/footer and theme presentation in `LandingPage.ts`/`LandingHero.ts` without breaking existing navigation or pause controls. Keep the workspace illustration honest: a static example must be clearly identified; a working demo would require separate implementation and checks.

Use subtle hover/focus and panel transitions from the shared tokens. Avoid introducing entrance animation that delays the primary CTA or moves forms during typing. Preserve reduced-motion and any existing pause preference. Static images cannot verify the current animated figure's performance.

Implement in this order: shared public shell and access-denied state; landing hierarchy; catalog/course information hierarchy; account copy/states; Help and policy notices. No new authentication providers, recommendation engine, or documentation search service is needed for this scope.

Acceptance journeys: landing → catalog filter → course → sign-in → return to enrollment; forgot password → generic confirmation → valid/expired reset; verification resend/error/success; invite → correct account → join. Check empty and failed catalog loads separately. Confirm direct error links use a complete shell, policy status remains accurate, consent links lead to the intended documents/state, and all controls work with keyboard, both themes, and reduced motion. Use desktop captures at 1440×900, with full-page images only where needed.
